Add two functions to the existing python3 inline block in bin/lint.sh:

**Function 1: Contradiction candidate detection (AGENTS.md section 11.3 step 7)**

This addresses the consensus review concern that "2+ sources in same section" is too broad. The narrowed heuristic:

1. For each wiki page, read its `type` from frontmatter. **Skip pages where type is `comparison` or `overview`** -- these are inherently multi-source by design and would generate constant false positives.

2. For remaining pages (entity, concept, source), parse the body into sections. A "section" starts at a `## ` or `### ` heading and ends at the next heading of equal or higher level, or end of file.

3. For each section, extract all `[prov:]` markers and collect distinct `source_id` values (the part before `#`).

4. If a section contains provenance markers from 2+ different source_ids, check whether existing `[contradiction:]` markers already cover that source pair. **Normalize source pairs lexicographically** so `A vs B` and `B vs A` are treated as the same pair.

5. For each NEW (not-yet-acknowledged) multi-source pair in the section, produce a finding:
   `warning|contradiction|<page_path>|Potential contradiction candidate in section "<section_heading>": claims from <source_a_id> and <source_b_id> (agent review needed)`

6. The finding explicitly says "candidate" and "agent review needed" -- the lint does NOT assert these ARE contradictions. The LLM agent running the lint workflow reviews flagged sections and promotes confirmed disagreements to `[contradiction:]` inline markers.

**Important constraints:**
- Report-only (per D-19) -- no auto-fix for contradiction candidates
- Severity is always `warning` (per D-06)
- Do NOT attempt semantic analysis -- strictly provenance-marker-based
- `type: comparison` and `type: overview` pages are EXCLUDED (addresses Codex HIGH + Gemini MEDIUM concern)
- Source pairs are normalized lexicographically to prevent A-vs-B and B-vs-A duplicates

**Function 2: has_contradictions frontmatter sync (AGENTS.md section 11.3 step 8)**

This addresses the consensus review concern about frontmatter drift.

1. For each wiki page, scan the body for `[contradiction:` markers (regex: `\[contradiction:[^\]]+\]`).

2. Read `has_contradictions` from frontmatter.

3. If markers exist in body AND `has_contradictions` is `false` (or missing): flag as finding `warning|contradiction-sync|<path>|has_contradictions should be true (found N [contradiction:] markers)`. If `--fix` is passed, update the frontmatter to `has_contradictions: true`.

4. If NO markers exist in body AND `has_contradictions` is `true`: flag as finding `warning|contradiction-sync|<path>|has_contradictions should be false (no [contradiction:] markers found)`. If `--fix` is passed, update the frontmatter to `has_contradictions: false`.

5. This is a mechanical, deterministic auto-fix -- the boolean simply reflects reality.

**Integration with existing code:**
- Add both functions alongside existing check functions (orphan, crossref, stale, etc.)
- Hook into the main check orchestrator
- Contradiction candidates: skippable via `--category contradiction`
- has_contradictions sync: runs as part of `--category contradiction` AND as part of `--category yaml` (since it's frontmatter validation)
- Findings feed into the existing accumulator and appear in the lint report

Add two knowledge gap detection functions to the python3 inline block in bin/lint.sh:

**1. Red link detection (per D-20, GAP-01):**

Using the wikilink extraction and resolution map already built for orphan detection:

- Collect all unresolved wikilinks (targets that don't match any known page id, title, or alias after case-insensitive normalization)
- For each unresolved link, track which pages reference it and whether it appears in a TL;DR or Key Facts section
- TL;DR/Key Facts detection: check if the wikilink appears in text between a `## TL;DR` or `## Key Facts` heading and the next `## ` heading
- **Flagging rules (per D-20):**
  - Flag if the unresolved link appears on 2+ distinct pages
  - Flag if the unresolved link appears in any TL;DR or Key Facts section (regardless of frequency)
- For each flagged red link, produce:
  `info|gap|red-link:<link_target>|Unresolved wikilink on N pages: <page1>, <page2>, ... Suggested question: What is <link_target> and how does it relate to the pages that reference it?`

**2. Sparse source coverage (per D-21, D-22, GAP-02):**

- Collect all unique `knowledge_domain` values from wiki page frontmatter (use `knowledge_domain` consistently for both classification and counting, per Codex review concern about mixing classification systems)
- For each knowledge_domain value, count the number of source pages (`type: source`) that have the SAME `knowledge_domain` value
- **Maturity guardrail (per D-22):** Only run this check when:
  - Wiki has 5+ distinct non-empty knowledge_domain values
  - At least 3 knowledge_domain values have 2+ source pages
  If guardrail not met, produce: `info|gap|maturity|Sparse coverage check skipped: wiki needs 5+ domains with 3+ having 2+ sources (currently N domains, M meet threshold)`
- If guardrail met, compute median source count across domains. Flag domains with source count < median/2 (or 0 sources):
  `info|gap|sparse:<domain>|Domain "<domain>" has N sources vs median M. Consider: <suggested question>`

**3. Question suggestions (per D-23, LINT-06):**

For each gap finding, include a suggested investigative question inline in the finding message:
- Red links: "What is <link_target> and how does it relate to the pages that reference it?"
- Sparse coverage with 0 sources: "What are your key interests or references in <domain>?"
- Sparse coverage with few sources: "What additional perspectives on <domain> would strengthen coverage?"

**Integration:**
- Both functions hook into the main check orchestrator
- Category name: `gap` (covers both red links and sparse coverage)
- Skippable via `--category gap`
- Findings are severity: info (per D-17)
- Report-only (per D-19)
