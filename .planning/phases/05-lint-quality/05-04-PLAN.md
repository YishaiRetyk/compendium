  <action>
Run the full lint workflow and validate results:

1. Run `bash bin/lint.sh wiki/` (without --dry-run, without --fix) to generate the full report.

2. Capture and review stdout output. Verify it contains:
   - Error/Warning/Info counts
   - Top findings listed
   - Path to lint-report.md

3. Read `wiki/maintenance/lint-report.md` and verify:
   - Valid YAML frontmatter with id: lint-report, type: overview
   - Sections for Errors, Warnings, Info with counts
   - At least one finding in each severity tier (or a rational explanation if a tier is empty)

4. Read `wiki/log.md` and verify a lint log entry was appended with:
   - Header format: `## [YYYY-MM-DD] lint | wiki health check`
   - findings count
   - auto_fixes count (should be 0 since --fix was not used)

5. Run `bash bin/lint.sh wiki/ --dry-run` and verify it does NOT modify lint-report.md or log.md.

6. Run `bash bin/lint.sh wiki/ --category orphan` and verify it runs only orphan checks.

7. **Coverage check:** Verify these finding categories appear in the report or stdout:
   - yaml (frontmatter validation)
   - provenance (ref validation)
   - orphan (no inbound links)
   - crossref (missing links between related pages)
   - stale (decay-based staleness)
   - contradiction (multi-source sections)
   - gap (red links or sparse coverage)
   
   If any category produces zero findings, investigate whether that's correct for the current wiki state. The current wiki is small (10 pages, all recently created, all by the same set of sources) so some categories may legitimately have zero findings (e.g., no actual stale claims if all were ingested recently). Document the rationale for any empty category.

8. If any issues are found (crashes, malformed output, missing categories), fix them in bin/lint.sh before proceeding to human review.
  </action>
