    **Section 9: Structured Operations and Executor Model** (~60 lines)
    Per D-03, SCHM-05:

    Define the four wiki mutation operations:

    1. **UPDATE** -- Modify an existing page with new information
       - Add new claims with provenance to existing sections
       - Update `updated_at` in frontmatter
       - Preserve existing provenance markers (do not remove)
       - Add new source IDs to `sources` list in frontmatter
       - Log: `"UPDATE <page_id>: <one-line rationale>"`

    2. **MERGE** -- Combine two pages covering the same concept
       - Create merged page with union of claims, preserving all provenance
       - Set `supersedes` on new page to list both merged page IDs
       - Set `superseded_by` on both old pages to point to new page
       - Set `status: superseded` on both old pages
       - Move old pages content to a brief redirect note
       - Log: `"MERGE <page_a> + <page_b> -> <new_page>: <rationale>"`

    3. **SUPERSEDE** -- Mark a claim or page as replaced by newer information
       - Update the page's `superseded_by` field with the replacing page ID
       - Set `status: superseded` on the old page
       - Add a note at the top of the old page: `> This page has been superseded by [[New Page]].`
       - Log: `"SUPERSEDE <old_page> -> <new_page>: <rationale>"`

    4. **ARCHIVE** -- Move outdated content out of active wiki
       - Set `status: archived` on the page
       - Remove from `wiki/index.md` active listings (move to an "Archived" section if one exists)
       - Page remains in its directory (do NOT delete or move files)
       - Log: `"ARCHIVE <page_id>: <rationale>"`

    **Executor model:** The LLM proposes operations. Before applying, it validates:
    - Target page exists (for UPDATE, SUPERSEDE, ARCHIVE)
    - Both pages exist and are distinct (for MERGE)
    - All provenance references in new content resolve to known sources
    - Frontmatter is valid YAML with all required fields

    Every operation MUST be logged in `wiki/log.md` with timestamp, operation type, affected pages, and rationale.

    **Section 10: Compiler Pipeline** (~50 lines)
    Per SCHM-02, D-04:

    Define the multi-pass compilation pipeline for ingesting a source:

    ```
    diff -> extract -> merge -> lint [-> optional follow-on passes]
    ```

    **Pass 1: Diff** -- Compare the new source against current wiki state
    - Read `wiki/index.md` to identify existing pages on related topics
    - Read TL;DR and Key Facts of related pages
    - Determine: What does this source add that the wiki doesn't already cover?
    - Output: A mental model of new vs. existing knowledge (not a file)

    **Pass 2: Extract** -- Pull structured knowledge from the source
    - Classify source type (article, paper, transcript, journal, data, image-heavy)
    - Extract claims, entities, and relationships with provenance locators
    - Create a source summary page in `wiki/sources/` with all extracted claims
    - Each claim gets a `[prov:source_id#locator]` marker

    **Pass 3: Merge** -- Integrate extracted knowledge into the wiki
    - UPDATE existing pages with new claims (using UPDATE operation)
    - Create new pages for entities/concepts not yet in the wiki
    - Generate wikilinks between related pages (first mention only)
    - MERGE pages if the new source reveals two existing pages cover the same topic

    **Pass 4: Lint** -- Verify consistency after merge
    - Check all new `[prov:...]` markers resolve to valid sources
    - Check all new wikilinks point to existing pages or are intentional red links
    - Check frontmatter is complete and valid on all modified pages
    - Check for contradictions between new claims and existing claims

    **Optional follow-on passes:** summary regeneration, image processing, structural reorganization. These are not required on every ingest.

    **Section 11: Workflows** (~120 lines)
    Per D-03, D-04, SCHM-02:
    All four workflows defined with prescriptive step-by-step instructions.

    **11.1 Ingest Workflow**
    Step-by-step procedure for ingesting a new source:
    1. User places source document in `sources/YYYY/YYYY-MM/YYYY-MM-DD-slug/` (bundle) or `sources/YYYY/YYYY-MM/YYYY-MM-DD-slug.md` (single file)
    2. LLM reads the source document completely
    3. LLM classifies the source type: article, paper, transcript, journal entry, data file, image-heavy
    4. LLM runs the compiler pipeline (Section 10): diff -> extract -> merge -> lint
    5. LLM creates source summary page in `wiki/sources/<source_id>.md` with full frontmatter including `path`, `content_hash`, `ingested_at`
    6. LLM updates or creates entity/concept/overview pages as needed (using UPDATE or new page creation)
    7. LLM updates `wiki/index.md` with new/modified pages
    8. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] ingest | <source title>`
    9. LLM commits: `ingest(<source-slug>): <one-line summary>`

    **11.2 Query Workflow**
    Step-by-step procedure for answering a question:
    1. LLM reads `wiki/index.md` to find relevant pages
    2. LLM reads TL;DR and Key Facts of relevant pages (progressive disclosure)
    3. LLM reads Detail sections only where shallow content is insufficient
    4. LLM synthesizes answer with citations to specific pages and provenance markers
    5. If the answer produces useful synthesis: LLM writes it back to the wiki as a new or updated page (mandatory write-back)
    6. LLM checks for delta compilation: are there sources in `wiki/sources/` relevant to this query whose knowledge hasn't been fully compiled into topic pages? If yes, compile the missing synthesis.
    7. LLM updates `wiki/index.md` if new pages were created
    8. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] query | <question summary>`
    9. LLM commits: `query(<topic>): <one-line summary>`

    **11.3 Lint Workflow**
    Step-by-step procedure for health-checking the wiki:
    1. LLM reads `wiki/index.md` for full page inventory
    2. Check for orphan pages: pages with no inbound wikilinks from other pages
    3. Check for missing cross-references: related pages that should link to each other but don't
    4. Check for stale claims: claims with `checked_at` dates older than threshold, or pages with `epistemic_status: stale`
    5. Check for contradictions: claims on the same topic that disagree across pages
    6. Check for knowledge gaps: red links (unresolved wikilinks) that appear across multiple pages, suggesting a page should be created
    7. Check for source coverage gaps: domains with few sources relative to others
    8. Report findings in structured format
    9. Suggest new questions to investigate and new sources to look for
    10. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] lint | <scope>`
    11. LLM commits: `lint(<scope>): <one-line summary>`

    **11.4 Reflect Workflow**
    Step-by-step procedure for recording structural decisions:
    1. Trigger: after major ingests, reorganizations, or periodic review
    2. LLM identifies what structural change was made (page merges, topic reorganization, schema updates)
    3. LLM creates a decision page in `wiki/overviews/` with `type: overview` and sections per D-23: TL;DR -> Decision -> Why -> Alternatives Considered -> Consequences -> Sources
    4. Decision page documents: what framing was adopted, what it replaced, what alternatives were considered
    5. LLM updates `wiki/index.md` with the decision page
    6. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] reflect | <scope>`
    7. LLM commits: `reflect(<scope>): <one-line summary>`

    **Section 13: Privacy Routing** (~40 lines)
    Per D-29, D-30, D-31, BNDY-02:

    **Three-level precedence** (most specific wins):
    1. Explicit `privacy` field in item frontmatter (authoritative)
    2. Enclosing directory default (operational convenience)
    3. System default: `local_only` (fail-closed)

    Privacy tiers:
    - `local_only` -- NEVER sent to cloud LLM APIs. Processed only by local models.
    - `cloud_safe` -- May be sent to cloud LLM APIs for processing.

    Rules:
    - If frontmatter `privacy` field is set, it is authoritative
    - If not set, check directory: `sources/local-only/` implies `local_only`, `sources/cloud-safe/` implies `cloud_safe`
    - If directory provides no signal, default to `local_only`
    - If directory and frontmatter conflict, prefer the STRICTER setting (i.e., `local_only` wins)
    - Unclassified items are `local_only` by default (fail-closed)
    - The LLM MUST check privacy classification before sending any content to a cloud API
    - Wiki pages inherit the strictest privacy tier of their contributing sources

    **Section 14: Scaling Boundaries** (~50 lines)
    Per D-27, D-28, BNDY-01, BNDY-03:

    **Important:** These are provisional heuristics, not hard boundaries. Validate through use.

    **Tier 1: Markdown-First Baseline (v1)**
    - Everything is markdown files and YAML frontmatter
    - `wiki/index.md` is the primary navigation mechanism
    - Full lint scans all pages
    - Works well for: up to ~100-200 pages, ~50-100 sources
    - Signal that you're outgrowing this: index.md becomes slow to navigate, LLM context fills up scanning it

    **Tier 2: Split Index**
    - When the single index becomes unwieldy (approximately a few hundred pages)
    - Split into per-type or per-domain indexes: `wiki/index-entities.md`, `wiki/index-concepts.md`, etc.
    - LLM reads the relevant sub-index instead of the full index
    - Signal to upgrade: LLM frequently reads pages irrelevant to the query because index is too broad

    **Tier 3: Incremental Lint**
    - When full lint becomes too expensive to run routinely
    - Track which pages changed since last lint (via git diff or log.md timestamps)
    - Only lint changed pages and their direct neighbors (pages they link to or are linked from)
    - Signal to upgrade: lint takes so long that you stop running it

    **Tier 4: DB-Backed Metadata**
    - When provenance queries, search, or concurrency become awkward in pure markdown
    - Add SQLite (or similar) for metadata: source registry, provenance index, search index
    - Markdown pages remain the human-facing artifact; DB is an acceleration layer
    - Signal to upgrade: provenance validation is slow, search needs more than grep, multiple agents need concurrent access

    Note: These tiers are additive. Each builds on the previous rather than replacing it.

    **Section 15: Tooling and Integrations** (~30 lines)

    **Obsidian** (primary human interface):
    - Graph View: visualize wiki link structure. Meaningful links only (per Section 8 conventions).
    - Dataview plugin: query frontmatter fields with TABLE/LIST syntax. All frontmatter fields defined in Section 5 are queryable.
    - Properties: Obsidian 1.4+ supports typed frontmatter editing. Fields render as editable properties in the sidebar.
    - Aliases: `aliases` frontmatter field enables Obsidian to resolve alternative page names automatically.

    **Git** (version control):
    - All changes tracked in git with conventional commits (per Section 3)
    - History provides full audit trail of wiki evolution
    - Branching available for experimental restructuring

    **Optional future tools** (not required for v1):
    - qmd or similar local search engine for hybrid BM25/vector search
    - Obsidian Web Clipper for source acquisition from web
    - Marp plugin for generating slide decks from wiki content
