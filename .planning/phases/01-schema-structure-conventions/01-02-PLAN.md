    **Section 9: Structured Operations and Executor Model** (~70 lines)
    Per D-03, SCHM-05:

    Start with a short operations vocabulary table (addresses Codex suggestion):
    ```
    | Operation  | Verb      | What It Does                                      |
    |------------|-----------|---------------------------------------------------|
    | UPDATE     | Modify    | Add new information to an existing page            |
    | MERGE      | Combine   | Unify two pages covering the same concept          |
    | SUPERSEDE  | Replace   | Mark a page/claim as replaced by newer information |
    | ARCHIVE    | Retire    | Move outdated content out of active wiki           |
    ```

    Then define each operation in detail:

    1. **UPDATE** -- Modify an existing page with new information
       - Add new claims with provenance to existing sections
       - Update `updated_at` in frontmatter
       - Preserve existing provenance markers (do not remove)
       - Add new source IDs to `sources` list in frontmatter
       - Log: `"UPDATE <page_id>: <one-line rationale>"`

    2. **MERGE** -- Combine two pages covering the same concept
       - Create merged page with union of claims, preserving all provenance
       - Set `supersedes` on new page to list both merged page IDs
       - Set `superseded_by` on both old pages to point to new page
       - Set `status: superseded` on both old pages
       - Move old pages content to a brief redirect note
       - Log: `"MERGE <page_a> + <page_b> -> <new_page>: <rationale>"`

    3. **SUPERSEDE** -- Mark a claim or page as replaced by newer information
       - Update the page's `superseded_by` field with the replacing page ID
       - Set `status: superseded` on the old page
       - Add a note at the top of the old page: `> This page has been superseded by [[New Page]].`
       - Log: `"SUPERSEDE <old_page> -> <new_page>: <rationale>"`

    4. **ARCHIVE** -- Move outdated content out of active wiki
       - Set `status: archived` on the page
       - Remove from `wiki/index.md` active listings (move to an "Archived" section if one exists)
       - Page remains in its directory (do NOT delete or move files)
       - Log: `"ARCHIVE <page_id>: <rationale>"`

    **Executor model:** The LLM proposes operations. Before applying, it validates:
    - Target page exists (for UPDATE, SUPERSEDE, ARCHIVE)
    - Both pages exist and are distinct (for MERGE)
    - All provenance references in new content resolve to known sources
    - Frontmatter is valid YAML with all required fields
    - Privacy classification is respected (no local_only content sent to cloud)

    Every operation MUST be logged in `wiki/log.md` with timestamp, operation type, affected pages, and rationale.

    **Section 10: Compiler Pipeline (Conceptual Model)** (~60 lines)
    Per SCHM-02, D-04. Addresses Codex review: clearly label this as the CONCEPTUAL lifecycle model, distinct from the procedural workflows in Section 11.

    Open with: "This section describes the conceptual compilation model -- the state machine that source material passes through. Section 11 (Workflows) provides the step-by-step operator procedures that implement this model."

    Define the multi-pass compilation pipeline for ingesting a source:

    ```
    Source -> [Classify] -> [Diff] -> [Extract] -> [Merge] -> [Lint] -> Wiki
    ```

    **Pass 0: Classify** -- Determine source type
    - Types: article, paper, transcript, journal entry, data file, image-heavy
    - Different source types require different extraction logic
    - Output: source type classification for Pass 2

    **Pass 1: Diff** -- Compare the new source against current wiki state
    - Read `wiki/index.md` to identify existing pages on related topics
    - Read TL;DR and Key Facts of related pages
    - Determine: What does this source add that the wiki doesn't already cover?
    - Output: A mental model of new vs. existing knowledge (not a file)

    **Pass 2: Extract** -- Pull structured knowledge from the source
    - Apply type-appropriate extraction (e.g., papers get abstract/methodology/results; transcripts get timestamped claims)
    - Extract claims, entities, and relationships with provenance locators
    - Create a source summary page in `wiki/sources/` with all extracted claims
    - Each claim gets a `[prov:source_id#locator]` marker
    - Output: source summary page, list of claims with provenance

    **Pass 3: Merge** -- Integrate extracted knowledge into the wiki
    - UPDATE existing pages with new claims (using UPDATE operation from Section 9)
    - Create new pages for entities/concepts not yet in the wiki
    - Generate wikilinks between related pages (first mention only)
    - MERGE pages if the new source reveals two existing pages cover the same topic
    - Output: updated/new wiki pages

    **Pass 4: Lint** -- Verify consistency after merge
    - Check all new `[prov:...]` markers resolve to valid sources
    - Check all new wikilinks point to existing pages or are intentional red links
    - Check frontmatter is complete and valid on all modified pages
    - Check for contradictions between new claims and existing claims
    - Output: list of issues found (if any)

    **Optional follow-on passes:** summary regeneration, image processing, structural reorganization. These are not required on every ingest.

    **Section 11: Workflows** (~160 lines)
    Per D-03, D-04, SCHM-02. Addresses Codex HIGH review feedback: each workflow must include trigger, inputs, ordered steps, output artifacts, commit convention, and abort/escalation conditions.

    Open with: "These are the operator procedures that implement the conceptual pipeline (Section 10). Each workflow is a complete recipe an LLM agent follows step-by-step."

    **11.1 Ingest Workflow**
    ```
    Trigger:  User places a new source document and requests ingestion
    Inputs:   Source file at sources/YYYY/YYYY-MM/YYYY-MM-DD-slug/ (or .md)
    Outputs:  Source summary page, updated wiki pages, updated index, updated log
    Commit:   ingest(<source-slug>): <one-line summary>
    ```

    Steps:
    1. User places source document in `sources/YYYY/YYYY-MM/YYYY-MM-DD-slug/` (bundle) or `sources/YYYY/YYYY-MM/YYYY-MM-DD-slug.md` (single file)
    2. LLM reads the source document completely
    3. LLM classifies the source type: article, paper, transcript, journal entry, data file, image-heavy (Pipeline Pass 0)
    4. LLM runs diff pass: reads `wiki/index.md`, identifies related existing pages, reads their TL;DR/Key Facts (Pipeline Pass 1)
    5. LLM runs extract pass: extracts claims with provenance locators, creates source summary page in `wiki/sources/<source_id>.md` with full frontmatter including `path`, `content_hash`, `ingested_at` (Pipeline Pass 2)
    6. LLM runs merge pass: updates or creates entity/concept/overview pages using UPDATE operations, generates wikilinks (Pipeline Pass 3)
    7. LLM runs lint pass: verifies provenance references resolve, wikilinks are valid, frontmatter is complete (Pipeline Pass 4)
    8. LLM updates `wiki/index.md` with new/modified pages
    9. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] ingest | <source title>`
    10. LLM commits: `ingest(<source-slug>): <one-line summary>`

    Abort conditions: If source is unreadable, if source duplicates an already-ingested source (check `content_hash`), if privacy classification cannot be determined. In these cases, log the failure in `wiki/log.md` and do NOT create partial wiki pages.

    **11.2 Query Workflow**
    ```
    Trigger:  User asks a question about the wiki contents
    Inputs:   User question (natural language)
    Outputs:  Answer with citations, optionally new/updated wiki pages, updated index/log
    Commit:   query(<topic>): <one-line summary>
    ```

    Steps:
    1. LLM reads `wiki/index.md` to find relevant pages
    2. LLM reads TL;DR and Key Facts of relevant pages (progressive disclosure)
    3. LLM reads Detail sections only where shallow content is insufficient
    4. LLM synthesizes answer with citations to specific pages and provenance markers
    5. If the answer produces useful synthesis: LLM writes it back to the wiki as a new or updated page (mandatory write-back per QURY-04)
    6. LLM checks for delta compilation: are there sources in `wiki/sources/` relevant to this query whose knowledge hasn't been fully compiled into topic pages? If yes, compile the missing synthesis.
    7. LLM updates `wiki/index.md` if new pages were created
    8. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] query | <question summary>`
    9. LLM commits (only if wiki was modified): `query(<topic>): <one-line summary>`

    Abort conditions: If no relevant pages exist and no sources exist on the topic, inform the user rather than hallucinating an answer. Log the gap in `wiki/log.md`.

    **11.3 Lint Workflow**
    ```
    Trigger:  User requests a health check, or periodically after several ingests
    Inputs:   wiki/ directory (all pages)
    Outputs:  Structured findings report, optionally fixed pages, updated log
    Commit:   lint(<scope>): <one-line summary>
    ```

    Steps:
    1. LLM reads `wiki/index.md` for full page inventory
    2. Check for orphan pages: pages with no inbound wikilinks from other pages
    3. Check for missing cross-references: related pages that should link to each other but don't
    4. Check for stale claims: claims with `checked_at` dates older than threshold, or pages with `epistemic_status: stale`
    5. Check for contradictions: claims on the same topic that disagree across pages
    6. Check for knowledge gaps: red links (unresolved wikilinks) that appear across multiple pages, suggesting a page should be created
    7. Check for source coverage gaps: domains with few sources relative to others
    8. Report findings in structured format (list of issues by category)
    9. Suggest new questions to investigate and new sources to look for
    10. Fix trivially fixable issues (e.g., add missing cross-references, update stale epistemic_status)
    11. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] lint | <scope>`
    12. LLM commits: `lint(<scope>): <one-line summary of findings and fixes>`

    Abort conditions: If wiki is empty (no pages beyond index.md and log.md), report that and skip.

    **11.4 Reflect Workflow**
    ```
    Trigger:  After major ingests, reorganizations, or periodic review
    Inputs:   Recent changes (from log.md or git history)
    Outputs:  Decision record page, updated index/log
    Commit:   reflect(<scope>): <one-line summary>
    ```

    Steps:
    1. LLM identifies what structural change was made (page merges, topic reorganization, schema updates)
    2. LLM creates a decision page in `wiki/overviews/` with `type: overview` and sections per D-23: TL;DR -> Decision -> Why -> Alternatives Considered -> Consequences -> Sources
    3. Decision page documents: what framing was adopted, what it replaced, what alternatives were considered
    4. LLM updates `wiki/index.md` with the decision page
    5. LLM appends entry to `wiki/log.md`: `## [YYYY-MM-DD] reflect | <scope>`
    6. LLM commits: `reflect(<scope>): <one-line summary>`

    Abort conditions: If no structural changes have been made since last reflection, skip.

    **Section 13: Privacy Routing** (~60 lines)
    Per D-29, D-30, D-31, BNDY-02. Addresses Codex HIGH review feedback: include a precise precedence table and at least 5 worked examples proving fail-closed behavior.

    **Three-level precedence** (most specific wins):
    1. Explicit `privacy` field in item frontmatter (authoritative)
    2. Enclosing directory default (operational convenience)
    3. System default: `local_only` (fail-closed)

    Privacy tiers:
    - `local_only` -- NEVER sent to cloud LLM APIs. Processed only by local models.
    - `cloud_safe` -- May be sent to cloud LLM APIs for processing.

    Rules:
    - If frontmatter `privacy` field is set, it is authoritative
    - If not set, check directory: `sources/local-only/` implies `local_only`, `sources/cloud-safe/` implies `cloud_safe`
    - If directory provides no signal, default to `local_only`
    - If directory and frontmatter conflict, prefer the STRICTER setting (i.e., `local_only` wins)
    - Unclassified items are `local_only` by default (fail-closed)
    - The LLM MUST check privacy classification before sending any content to a cloud API
    - Wiki pages inherit the strictest privacy tier of their contributing sources

    **Privacy Decision Table** (addresses Codex HIGH concern):
    ```
    | # | Frontmatter `privacy` | Directory             | Result       | Why                                   |
    |---|----------------------|-----------------------|-------------|---------------------------------------|
    | 1 | cloud_safe           | sources/cloud-safe/   | cloud_safe  | Both agree: cloud_safe                |
    | 2 | local_only           | sources/cloud-safe/   | local_only  | Frontmatter is stricter, stricter wins|
    | 3 | cloud_safe           | sources/local-only/   | local_only  | Directory is stricter, stricter wins  |
    | 4 | (not set)            | sources/cloud-safe/   | cloud_safe  | No frontmatter, directory provides signal |
    | 5 | (not set)            | sources/2026/2026-04/ | local_only  | No frontmatter, no privacy directory signal, system default |
    | 6 | (not set)            | (no directory signal)  | local_only  | Fail-closed: unknown = local_only     |
    | 7 | local_only           | (no directory signal)  | local_only  | Explicit local_only                   |
    ```

    Add a note: "When in doubt, the answer is `local_only`. The system is designed to fail safe -- it is better to under-share than to accidentally send private content to a cloud API."

    **Wiki page privacy inheritance:** When a wiki page cites sources with mixed privacy tiers (e.g., one `local_only` source and one `cloud_safe` source), the wiki page inherits `local_only` (the strictest tier among its sources).

    **Section 14: Scaling Boundaries** (~60 lines)
    Per D-27, D-28, BNDY-01, BNDY-03. Addresses Codex MEDIUM review: require each tier to include size heuristics, expected pain points, and recommended agent behavior changes.

    **Important:** These are provisional heuristics, not hard boundaries. Validate through use.

    **Tier 1: Markdown-First Baseline (v1)**
    - Everything is markdown files and YAML frontmatter
    - `wiki/index.md` is the primary navigation mechanism
    - Full lint scans all pages
    - Approximate capacity: up to ~100-200 pages, ~50-100 sources
    - Pain points at limit: index.md becomes slow to navigate, LLM context fills up scanning it, full lint takes multiple minutes
    - Agent behavior: read full index, scan all pages during lint
    - Signal you're outgrowing this: index.md exceeds ~500 lines, LLM frequently asks for pages irrelevant to the query

    **Tier 2: Split Index**
    - When the single index becomes unwieldy (approximately a few hundred pages)
    - Split into per-type or per-domain indexes: `wiki/index-entities.md`, `wiki/index-concepts.md`, etc.
    - Main `wiki/index.md` becomes a meta-index pointing to sub-indexes
    - Agent behavior: read relevant sub-index instead of full index
    - Pain points at limit: even sub-indexes become large, cross-type queries require reading multiple sub-indexes
    - Signal to upgrade: sub-indexes exceed ~200 entries each, cross-domain queries are slow

    **Tier 3: Incremental Lint**
    - When full lint becomes too expensive to run routinely
    - Track which pages changed since last lint (via git diff or log.md timestamps)
    - Only lint changed pages and their direct neighbors (pages they link to or are linked from)
    - Agent behavior: `git diff --name-only <last-lint-commit>` to scope lint
    - Pain points at limit: neighbor expansion still large, deep dependency chains missed
    - Signal to upgrade: lint takes so long that you stop running it

    **Tier 4: DB-Backed Metadata**
    - When provenance queries, search, or concurrency become awkward in pure markdown
    - Add SQLite (or similar) for metadata: source registry, provenance index, search index
    - Markdown pages remain the human-facing artifact; DB is an acceleration layer
    - Agent behavior: query DB for source/provenance lookups instead of scanning markdown
    - Pain points: requires maintaining DB sync with markdown, adds tooling dependency
    - Signal to upgrade: provenance validation is slow, search needs more than grep, multiple agents need concurrent access

    Note: These tiers are additive. Each builds on the previous rather than replacing it.

    **Section 15: Tooling and Integrations** (~30 lines)

    Note at top: "This section is informational, not normative. It describes tools the wiki is designed to work with, but does not mandate their installation."

    **Obsidian** (primary human interface):
    - Graph View: visualize wiki link structure. Meaningful links only (per Section 8 conventions).
    - Dataview plugin: query frontmatter fields with TABLE/LIST syntax. All frontmatter fields defined in Section 5 are queryable.
    - Properties: Obsidian 1.4+ supports typed frontmatter editing. Fields render as editable properties in the sidebar.

    - All changes tracked in git with conventional commits (per Section 3)

    **Optional future tools** (not required for v1):

    - Obsidian Web Clipper for source acquisition from web
