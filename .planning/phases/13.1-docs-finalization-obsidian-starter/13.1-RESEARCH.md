### Pattern 1: Token-ized template derived from canonical (OBSID-01/D-02)
**What:** Each `schema/obsidian/<type>.md` is the byte-near canonical template with auto-fill tokens inserted into the auto-fillable base fields, keeping identical field set + section order.
**When to use:** All six page types.
**Example (entity — derived from `schema/templates/entity.md`):**
```markdown
---
id:
title: {{title}}
type: entity
status: active
summary: ""
created_at: {{date:YYYY-MM-DD}}
updated_at: {{date:YYYY-MM-DD}}
sources: []
epistemic_status:
tags: []
domains: []
supersedes:
superseded_by:
privacy:
aliases: []
---
# (identical section order: TL;DR -> Key Facts -> Detail -> Related Pages -> Sources)
```
Note: D-01 says only `title`/`created_at`/`updated_at` auto-fill; user hand-types `id`, `summary`, `tags`. `{{date:YYYY-MM-DD}}` is pinned explicitly for safety (core default is already ISO, but explicit pinning survives a user who changed their global date-format setting — directly serves CLAUDE.md §3 ISO date rule). `[CITED: obsidian.md/help/plugins/templates]`

### Pattern 2: `codex exec` non-interactive ingest into scratch wiki (DEBT-02)
**What:** One-shot prompt that ingests the chosen raw source into an isolated scratch directory, writing files non-interactively.
**Example invocation (recommended):**
```bash

SCRATCH=$(mktemp -d)
# ... seed $SCRATCH with CLAUDE.md (or schema/AGENTS.template.md), an empty wiki/ skeleton,
#     and the chosen raw source under sources/2026/2026-04/2026-04-10-kahneman-prospect-theory/source.md ...

/home/yishai/.nvm/versions/node/v24.14.0/bin/codex exec \
  -C "$SCRATCH" \
  -s workspace-write \
  --skip-git-repo-check \
  -o "$SCRATCH/.codex-last-message.txt" \
  "Read CLAUDE.md (the wiki schema). Ingest the single raw source at \
   sources/2026/2026-04/2026-04-10-kahneman-prospect-theory/source.md into this wiki \
   following the §11.1 ingest workflow: create a source summary page plus entity/concept/ \
   comparison/overview pages with [prov:] provenance markers. Do not touch any file outside this directory."
```
**Flag rationale `[VERIFIED: codex exec --help]`:**
- `-C "$SCRATCH"` — working root = scratch dir (isolation; never touches live `wiki/`).
- `-s workspace-write` — lets the agent write files within the workspace (needed to create pages).
- `--skip-git-repo-check` — scratch dir need not be a git repo.
- `-o <file>` — capture the final agent message for the verification record.
- If `workspace-write` still prompts for approvals in this environment, fall back to `--dangerously-bypass-approvals-and-sandbox` (the docs label it EXTREMELY DANGEROUS; acceptable here because the working root is a throwaway `mktemp -d` scratch with only the seeded source — document the justification in `13.1-VERIFICATION.md`).
- Optionally `--json` for machine-parseable event stream if a transcript is wanted.

### Pattern 3: Structural-equivalence diff (D-07)
**What:** Compare two ingest outputs (and golden) on STRUCTURE, not prose.
**Method (practical):**
1. **Page set + types:** for each output dir, list `wiki/**/*.md`, extract `type:` from frontmatter → produce a sorted `(relative-dir, type)` multiset. PASS requires same multiset across {Claude, Codex, golden} modulo prose-only file naming. Golden = 1 entity, 3 concepts, 1 comparison, 1 overview, 2 sources `[VERIFIED: examples/kahneman counts]`.
2. **Provenance targets:** `grep -ohE '\[prov:[^]|]+' **/*.md` → normalize to `source_id#locator` set; compare sets. PASS requires same source IDs + locator targets (locator *shape* and target, e.g. `#sec:loss-aversion`, must match; prose around it may differ).
3. **Frontmatter validity:** run `bin/lint.sh --category yaml,provenance` against each scratch output → zero errors.
4. **Present diff:** a table in `agent-parity.md` / `13.1-VERIFICATION.md`: rows = {page-set, page-types, prov-source-IDs, prov-locator-targets, frontmatter-valid}; cols = {Claude vs golden, Codex vs golden, Claude vs Codex}; cells = MATCH / DIFFERS(noted). Prose differences listed separately as "expected variance, not a failure."

## Common Pitfalls

### Pitfall 1: Treating `.obsidianignore` as an enforced Obsidian feature (THE D-05 TENSION — RESOLVED)
**What goes wrong:** The plan assumes `examples/` is hidden from Dataview indexing, so it relocates fixtures or writes awkward query phrasing to dodge a zero-row result that won't actually occur.
**Why it happens:** The repo ships a `.obsidianignore` file with comments saying it "hides examples/ from the Obsidian graph view + content indexing." That claim is aspirational/conventional, not technical.
**Ground truth `[VERIFIED: live repo]`:**
- Obsidian has **no native `.obsidianignore` support**. Its real exclusion mechanism is `app.json`'s `userIgnoreFilters` (set via Settings → Files & Links → Excluded files).
- Live `.obsidian/app.json` is `{}` — `userIgnoreFilters` is **unset**. `graph.json` has empty `search`. Nothing in `bin/` converts `.obsidianignore` → `app.json`.
- The only consumer of `.obsidianignore` is `bin/release.sh` (release manifest) + human-readable docs (`docs/quickstart.md`, `examples.md`).
- Therefore: **Obsidian and Dataview currently index `examples/` fully.** A `FROM "examples/dataview-fixtures"` query returns rows today with zero config changes.
- Even Obsidian's real "Excluded files" setting primarily affects search/UI ranking and is documented as NOT reliably stopping Dataview indexing. `[CITED: forum.obsidian.md exclude-folder threads]`
**How to avoid (primary recommendation):**
1. Build `examples/dataview-fixtures/` and point the verification queries `FROM "examples/dataview-fixtures"`.
2. In the DEBT-01 render checklist, explicitly state: *"Do NOT add `examples/` to Settings → Files & Links → Excluded files for this render pass — the fixtures must remain indexed for Dataview."*
3. **Reconcile the convention drift:** the accuracy-pass on `examples.md` (D-10/D-11) must correct the `.obsidianignore` description to say what it actually is (a release-manifest + graph-hygiene *convention*, not an Obsidian-enforced indexing exclusion). This closes the doc/reality gap surfaced by D-05.
**Fallback (if user has a personal `userIgnoreFilters` excluding `examples/`):** the checklist directs them to temporarily remove `examples/` (or just `examples/dataview-fixtures/`) from Excluded files for the render pass. Secondary fallback: relocate fixtures outside `examples/` — but this loses the `example:true` lint-skip convention and adds maintenance, so it is the last resort, not the default.
