## Phase Boundary

Phase 13.1 delivers three distinct things now that the v1.1 feature surface (Phases 7–13) is stable:

1. **Docs finalization** — `/docs/reference/` is filled out against the shipped v1.1 surface. The three never-populated stubs (`schema-tour.md`, `privacy-model.md`, `examples.md`) get full authoring; a new `agent-parity.md` is created; the substantial existing docs (`brownfield.md`, `ci.md`, `three-layer-model.md`, `dataview-queries.md`, `release.md`) get a correctness pass; `docs/reference/index.md` is reconciled to list every file.

2. **Deferred v1.0 verifications executed end-to-end** — the three checks deferred since v1.0 Phase 4 are run and their results captured in `13.1-VERIFICATION.md`: DEBT-01 Obsidian render (wikilinks resolve, Dataview renders with expected row counts, `examples/` not in graph), DEBT-02 non-Claude (Codex) agent-parity ingest diff, DEBT-04 genuine write-back scenario.

3. **Minimal Obsidian starter** — `schema/obsidian/` ships page-type templates derived from `schema/templates/` plus a reference doc, closing the day-1 page-creation ergonomics gap. Explicitly NOT shipping dashboards, GTD views, hotkey bundles, custom CSS/themes, or prescribed review workflows (OBSID-03; deferred to backlog 999.6).

**In scope:** DEBT-01, DEBT-02, DEBT-04, OBSID-01, OBSID-02, OBSID-03 (see REQUIREMENTS.md). Building `examples/dataview-fixtures/`. Authoring/accuracy-passing reference docs. Executing + capturing the three verifications. The `schema/obsidian/` starter + its reference doc.

**Out of scope (LOCKED):** Obsidian dashboards, workflow-specific Dataview surfaces, hotkey bundles, custom CSS/theme files, prescribed review workflows (OBSID-03). No new product features. This phase does NOT run the final v1.1 closure gate — that is Phase 13.2 (CLOSE-01..04), which re-runs/audits 13.1's verification notes.

<decisions>
## Implementation Decisions

### Obsidian starter shape (OBSID-01/02/03)
- **D-01:** **Template format = Obsidian Templates-core tokens.** Ship plain-markdown page-type templates that use the built-in Templates *core* plugin tokens (`{{title}}`, `{{date}}`) so `title`/`created_at`/`updated_at` auto-fill on insert; the user still hand-types `id`, `summary`, `tags`. **No community-plugin dependency** (rejected Templater — adds a third-party install that borders on OBSID-03's "prescribed workflow"; rejected plain literal-placeholder markdown — worst ergonomics, nothing auto-fills).
- **D-02:** **Templates derive from `schema/templates/` without field/section drift** (OBSID-01 "no divergent field names or section order"). Cover the supported wiki page types — entity, concept, source-summary, comparison, overview, decision (mirror the six files in `schema/templates/`). The Obsidian templates are the token-ized counterparts of the canonical schema templates; the planner must guard against the two sets drifting apart.
- **D-03:** **Files + doc only — do NOT mutate `.obsidian/` config.** Ship the markdown templates under `schema/obsidian/` plus a reference doc (OBSID-02) whose "Setup (once)" section walks the user through enabling the Templates core plugin and pointing it at the template folder. The starter never edits the committed `.obsidian/` (`core-plugins.json` / template-folder setting). Rationale: works identically for fresh-starter AND brownfield-with-existing-vault users; pre-wiring would only help fresh-clone users and presumes a folder layout. (Rejected: pre-wiring the template folder + enabling the core plugin in committed `.obsidian/`.)

### Dataview verification fixtures (DEBT-01 / SC1)
- **D-04:** **Build `examples/dataview-fixtures/`** — a small purpose-built set of pages spanning page types / domains / statuses, each carrying `example: true` (so lint skips them), with a **documented expected row count per canonical Dataview query**. Deterministic, self-contained, matches SC1's literal path, counts can't drift. (Rejected: reuse `examples/kahneman/` — counts drift as the cluster is edited, and it's bigger than a focused fixture needs; rejected hybrid as over-maintenance.)
- **D-05:** **One fixture covers both SC1 vault states.** Include a few pages carrying `bootstrap_stage` frontmatter alongside normal ones, so a single Obsidian open exercises both "fresh-starter rendering" and "post-bootstrap `bootstrap_stage` fields render fine." Document expected counts once. (Rejected: two separate purpose-built snapshots; rejected reusing tests/phase-10|11 brownfield fixtures for a second open.)
- **KNOWN TENSION (researcher to resolve):** `.obsidianignore` currently excludes `examples/` from Obsidian **content indexing** (not just graph). A Dataview query `FROM "examples/dataview-fixtures"` would therefore return **zero rows**. The verification procedure must reconcile this — e.g., temporarily lift the ignore for the render pass, relocate the fixtures, or phrase the queries so they still resolve. This is the single most important unknown for DEBT-01.

### Manual-verification model (DEBT-01/02/04)
- **D-06:** **Execution split — I (Claude) own everything except the GUI.** I execute DEBT-04 (write-back scenario) end-to-end in-repo, and BOTH sides of DEBT-02: the Claude-side ingest AND the Codex-side ingest via **`codex exec`** (Codex CLI 0.135.0 confirmed installed at `/home/yishai/.nvm/versions/node/v24.14.0/bin/codex`). The **user does ONLY DEBT-01** (open Obsidian for the render check). I capture all results into `13.1-VERIFICATION.md`. (User override of the original "you do Codex" framing — the user explicitly authorized me to invoke the Codex CLI.)
- **D-07:** **Agent-parity tolerance = structural equivalence.** PASS if Claude and Codex both produce the **same set of pages, same page types, same provenance source IDs + locator targets, and valid frontmatter**. Claim prose / wording may differ freely — noted in the diff, not a failure. (Rejected: strict near-identical — turns normal LLM variance into noise; the "structural + provenance-resolves" higher bar was considered but not required for v1.1 parity — provenance *targets* matching is in-scope, full faithfulness resolution is not.)
- **D-08:** **Golden reference = the committed `examples/kahneman/` cluster.** Both agents re-ingest one Kahneman raw source into a **scratch wiki** (NOT the live `wiki/`); each output is diffed (per D-07) against `examples/kahneman/` as golden AND against each other. The bundled reference cluster is literally the canonical compiled output (1 entity, 3 concepts, 1 comparison, 1 overview, from 2 source-summary pages). (Rejected: captured Claude run as golden — bakes Claude's choices in as canonical; rejected agent-to-agent-only — DEBT-02 explicitly requires a "golden reference.")
- **D-09:** **DEBT-01 is prepared-and-await; Phase 13.1 is NOT blocked on the GUI step.** I ship the fixtures + a precise render checklist + a capture slot in `13.1-VERIFICATION.md`, and complete the agent-executable verifications (DEBT-02/04). DEBT-01 is marked "awaiting user render"; the user fills the slot when convenient; **Phase 13.2 closure (SC2) re-runs or audits it**. (Rejected: hard-block on the render — would keep the phase open on an async GUI action.)

### Docs depth & new files (DEBT/docs, SC4)
- **D-10:** **Stubs full + accuracy-pass the rest.** Fully author the 3 stubs (`schema-tour.md`, `privacy-model.md`, `examples.md`) and create `agent-parity.md`. Do a **correctness pass** on the substantial existing docs (`brownfield.md`, `ci.md`, `three-layer-model.md`, `dataview-queries.md`, `release.md`), editing **only where they drifted** from the shipped v1.1 surface — do not churn already-good content. Reconcile `docs/reference/index.md` to list every reference file (it currently omits `dataview-queries.md`, `commit-examples.md`, `setup-prerequisites.md`, and the new `agent-parity.md`). (Rejected: stubs-only — skips verifying the big docs didn't drift; rejected full-rewrite — high-effort churn.)
- **D-11:** **`agent-parity.md` standalone; merge-conflict + dataview-fixtures folded.** Create `docs/reference/agent-parity.md` as the distinct DEBT-02 deliverable (the structural-equivalence tolerance rubric + how to re-run the Codex parity diff). Keep merge-conflict recipes in `CONTRIBUTING.md` (Phase 9) — verify they're accurate and add an index pointer; **no new `merge-conflicts.md`**. Document the `examples/dataview-fixtures/` set + its expected row counts **inside `examples.md`**. (Rejected: each its own doc — more surface to keep accurate.)

### NEUTRALITY CONSTRAINT (binding on all docs work)
- **D-12:** Per CLAUDE.md §3, `docs/` and `schema/` are **template-public files**. All authored docs and Obsidian starter templates MUST use abstract placeholders (`<concept-slug>`, `<source-id>`, `<page-title>`, `<entity-name>`, `<YYYY-MM-DD-slug>`, `<term>`) — NEVER real slugs/IDs/terms from the user's private `wiki/` or any `local_only` content. The Kahneman example cluster is the ONLY sanctioned concrete example (it lives under `examples/`, is reference-only, and is already neutral). `bin/check-neutrality.sh` is a backstop, not the primary defense — prevent leaks at write time.

### Claude's Discretion
- Exact prose, structure, and section ordering of each authored reference doc (follow the existing house pattern: TL;DR + "See also" links as seen in `three-layer-model.md` / `dataview-queries.md`).
- Which single Kahneman raw source to use for the DEBT-02 parity ingest, and the exact scratch-wiki location/teardown for the parity + write-back runs.
- The precise composition of `examples/dataview-fixtures/` (how many pages, which type/domain/status spread) as long as each canonical query has a documented, non-trivial expected count and at least a couple of pages carry `bootstrap_stage`.
- Exact `13.1-VERIFICATION.md` evidence layout (follow the Phase 12.1 / 12.2 / 13 mirror format).
- Whether the write-back (DEBT-04) scratch run and the parity (DEBT-02) scratch run share one scratch wiki or use separate ones.
