## Codex Review

## Summary

The closure-gate design is mostly disciplined: it separates human GUI verification, docs/scope audit, and final mechanical closure; it uses existing gates instead of inventing new scripts; and it requires paired verification artifacts before archiving. The main weakness is evidentiary honesty: several checks can pass through edited prose, grep counts, or requirements-ledger consistency without independently proving the underlying behavior. The plans are usable, but Plan 03 in particular should avoid overstating what `requirements-sync` proves.

## Strengths

- Clear wave structure: Plan 03 correctly depends on Plan 01 and Plan 02.
- Good separation of concerns: render/parity/write-back, docs/scope audit, and final closure are distinct.
- Strong use of existing gates: `requirements-sync`, `check-neutrality`, `check-privacy`, and YAML lint are reused.
- Good explicit handling of the Codex runtime limitation: the plan forbids fabricating a Codex run.
- Good anti-scope discipline: no new scope-leak script, no new product features, no sudo/runtime remediation.
- Good finalization artifacts: requiring both `13.2-VERIFICATION.md` and independent `13.2-VERIFIER-REPORT.md` improves auditability.

## Concerns

- **HIGH:** Plan 03 over-claims that `requirements-sync` proves phases 12/12.1/12.2/13 were "re-run." `requirements-sync` proves ledger/artifact consistency, not behavioral non-regression. It can show every prior requirement is marked Complete consistently, but it does not re-execute validators, write gates, privacy scenarios, or audit scripts from those phases unless those commands are actually run again. The proposed wording should say "ledger consistency confirms no recorded verification drift," not "the mechanical gate is the re-run."

- **HIGH:** The human Obsidian render checkpoint can close on self-reported counts only. This may be acceptable by project decision, but the plan should not treat it as strong reproducible evidence unless it captures exact query text, plugin versions, and preferably screenshots or copied Dataview output. Otherwise DEBT-01 can pass with mistyped or misunderstood counts.

- **HIGH:** CLOSE-03 documentation consistency is manually scoped and may miss files. Plan 02 reviews `README.md`, `ROADMAP.md`, one reference doc, and one DR, but CLOSE-03 says README, docs, decision records, and roadmap. "docs" and "decision records" are plural. Other docs or DRs could contain stale/deferred-scope language and still pass.

- **MEDIUM:** Scope-leak grep terms are incomplete and may miss semantic leaks. A forbidden task engine could be described as "actions," "todo queue," "agenda," "recurrence," "due dates," "notifications," "workflow inbox," "event stream," "background job," or "database metadata" without matching the proposed terms. Manual classification is fine, but the search vocabulary is too narrow.

- **MEDIUM:** Grep-based acceptance criteria are fragile. Counts like `grep -c "Complete"` or `grep -c "blocked-on-host-runtime"` can pass while the relevant table row is wrong. Prefer anchored checks around REQ IDs, YAML fields, and specific section ranges.

- **MEDIUM:** The Codex disposition is defensible only if recorded as a coverage limitation. Calling it "blocked-on-host-runtime" is honest. Saying the Claude-vs-golden diff "carries the parity verdict" is weaker: it proves Claude output matches golden fixtures, not Codex parity. The final report should explicitly state Codex parity was not directly measured in this host environment.

- **MEDIUM:** Plan 03 commits only the dangling 12.2 report, then continues with many uncommitted closure edits. If `/gsd-complete-milestone` expects a clean tree or creates commits itself, this could leave a half-committed state. The plan should define commit boundaries for the SC1 DR, closure artifacts, and REQUIREMENTS flips.

- **LOW:** Plan 01 Task 2 runs `requirements-sync --strict` before Plan 03 closure artifacts exist. This is probably fine because `--strict` checks drift, not completeness, but the plan should explicitly confirm CLOSE rows are excluded from the exit-0 expectation until Plan 03.

- **LOW:** Plan 02's `git diff --stat` acceptance may be noisy if Plan 01 runs concurrently. Since the plans run in parallel in the same worktree, Plan 02 may see Plan 01 edits in `git diff --stat`. That acceptance should be scoped to files touched by Plan 02, or the wave should avoid shared-worktree parallelism.

## Suggestions

- Replace the Plan 03 "re-run" wording with: "Prior phase verification artifacts remain ledger-consistent; direct re-run/audit was limited to DEBT-01, DEBT-02, and DEBT-04 by decision."
- For Obsidian render evidence, require copied Dataview query blocks plus observed output, plugin versions, and optionally screenshots.
- Expand CLOSE-03 review scope with `rg` over all `README.md`, `docs/`, `wiki/decisions/`, `.planning/ROADMAP.md`, and `.planning/PROJECT.md` for deferred/backlog/boundary language.
- Expand scope-leak search terms: `todo`, `due date`, `notification`, `recurrence`, `agenda`, `inbox`, `next action`, `event stream`, `background job`, `queue`, `sqlite`, `database`, `scheduler`, `cron`.
- Use anchored checks such as `rg '^\- \[x\] \*\*CLOSE-0[1-4]\*\*: Complete'` and table-row-specific regexes instead of broad grep counts.
- In the final verifier report, explicitly distinguish "not measured due to host runtime" from "passed parity."
- Define final commit behavior before `/gsd-complete-milestone`: either commit all closure edits before archiving or state that the milestone command owns that commit.

## Risk Assessment

**Overall risk: MEDIUM.** The process is strong as a closure checklist, but weaker as behavioral proof. The largest risk is false confidence: `requirements-sync` and grep checks can prove documentation consistency while leaving runtime or semantic regressions untested. Tightening the claims and broadening the audit searches would make the gate much more defensible.

## Claude Review

# Cross-AI Plan Review — Phase 13.2 v1.1 Closure Verification Gate

## 1. Summary

This is a carefully-constructed three-plan closure gate that visibly learned from prior phases: it disciplines acceptance to exit codes over fragile greps, anticipates the single-source DEBT-02 asymmetry, separates REQUIREMENTS.md row-ownership cleanly across plans, and brackets the work with the two human checkpoints (render, archive) that genuinely require a human. The wave structure is sound and file-overlap-free. However, the gate is fundamentally a *consistency* gate, not a *correctness* gate — its strongest mechanical signal (`requirements-sync --strict --require-complete` exit 0) is produced by the same plans that flip the statuses, so it proves REQUIREMENTS.md ↔ VERIFICATION.md agreement, not that the underlying verifications actually hold. The single most important external-truth check (the human Obsidian render) has **no hard gate that blocks closure when the render counts are wrong**, and Plan 03's "phases 12/12.1/12.2/13 are proven via the zero-drift gate" framing over-claims what `requirements-sync` actually verifies. Both are fixable before execution.

## 2. Strengths

- **Exit-code-as-authority discipline.** Plan 01 Task 2 explicitly disarms the `grep -c "DRIFT"` trap (the sync table prints a `Drift` column header that echoes into the count) and routes acceptance through the exit code instead. This is exactly the right instinct and rare to see called out.
- **Clean row-ownership separation.** Plan 01 owns DEBT-01 rows; Plan 03 owns CLOSE-01..04 rows; Plan 01 is explicitly told "do NOT touch CLOSE-01..04." No REQUIREMENTS.md write contention across waves.
- **Wave 1 parallelism is genuinely safe** — Plan 01 (`13.1-VERIFICATION.md`, `REQUIREMENTS.md` DEBT rows, `agent-parity.md`) and Plan 02 (`README.md`, `ROADMAP.md`, `three-layer-model.md`, the boundary DR) have zero file overlap.
- **The single-source DEBT-02 asymmetry is handled honestly** — comparing Claude's single-source ingest only against the prospect-theory *subset* (not the full two-source golden) is the correct structural call, and it's documented as such.
- **Append-only / no-silent-correction handling at the human checkpoint** — Task 1 instructs the executor to record divergent counts verbatim and flag them rather than "correct to expected."
- **Prerequisite hygiene is folded in** — committing the dangling `12.2-VERIFIER-REPORT.md` *before* asserting committed-artifact consistency is the right ordering.

## 3. Concerns

- **[HIGH] DEBT-01 has no hard gate on a divergent render.** Plan 01 Task 1 surfaces a count mismatch (good), but Task 2's action **unconditionally** flips DEBT-01 → Complete "using the five counts reported," with no branch that halts closure if the counts ≠ 3/2/2/2/5. The Task 2 acceptance greps only check that the blanks are *filled*, not that they're *correct*. Since DEBT-01 *is* the Obsidian-render verification, a wrong-count render (which means the fixtures or the render are actually broken) still flips Complete, still clears the sole drift row, and still closes the milestone — with only a soft note in the SUMMARY. This is the textbook "milestone closes on false/failed evidence" path.
- **[MEDIUM] Plan 03's "re-run via the zero-drift gate" framing over-claims.** `requirements-sync` proves REQUIREMENTS.md ↔ VERIFICATION.md *documentation* consistency for phases 12/12.1/12.2/13; it does **not** re-run or detect functional regression in Obsidian rendering, agent-parity, or write-back. The required content line in 13.2-VERIFIER-REPORT.md asserts the zero-drift gate "IS the 're-run confirms nothing regressed' assertion for those landed phases" — that conflates consistency with regression-testing. The roadmap only asks the three *scenarios* to be run/audited at a point *after* those phases land; that's satisfied by running them once now. The honest framing is simpler and doesn't need the over-claim.
- **[MEDIUM] The zero-drift assertion is not independent of the CLOSE-02 evidence it depends on.** Flipping DEBT-01 in *both* REQUIREMENTS.md and 13.1-VERIFICATION.md is precisely what makes the drift check pass — the check is structurally incapable of catching a fabricated or wrong render. The only thing protecting CLOSE-01 from a bad CLOSE-02 is the human checkpoint, which (per the HIGH above) currently doesn't gate.
- **[MEDIUM] Scope-leak audit (CLOSE-04) keyword set is incomplete and the verify proxy is weaker than the action.** The forbidden set includes "high-frequency event ingest," but the grep has no term for it (no `event`, `ingest`, `webhook`, `stream`). Synonyms for the other forbidden items also escape (`tickler`, `agenda`, `due date`, `snooze`, `recurring`, `next action` is present but `agenda view` isn't). The Task 2 *verify* grep scans only `README.md docs/ AGENTS.md` while the *action* grep scans `wiki/ bin/ schema/` too — so the automated acceptance line cannot catch a leak in `bin/`/`schema/`/`wiki/`. And the `grep -v "...own[s]?..."` exclusion is broad enough to mask real hits. The audit ultimately rests on manual classification, including the genuinely hard "documented §14 future tier vs *shipped* premature implementation" distinction, which the grep cannot make.
- **[MEDIUM] agent-parity.md bakes maintainer-host-specific failure detail into a template-public doc, and risks reading as "parity confirmed."** Recording `blocked-on-host-runtime (AppArmor apparmor_restrict_unprivileged_userns=1)` is honest for the *planning* record, but agent-parity.md ships to adopters who clone the template — "this failed on the maintainer's machine due to their AppArmor setting" is odd payload for a generic reference doc. Separately, cross-agent parity was never empirically demonstrated (Codex produced 0 pages); the Claude-vs-golden diff proves *Claude* follows the golden, not that a *second* agent does. The disposition must read as **accepted-unverified**, not "parity holds, minor runtime hiccup" — otherwise PROJECT.md's "Multi-agent validation (Codex or other)" requirement closes on an over-claim. (D-02 authorizes the *acceptance*; it doesn't license the doc to imply verification.)
- **[MEDIUM] Plan 01 Task 3 acceptance is keyed to one exact em-dash literal.** `grep -c "pending — deferred to 13.2" … returns 0` uses `—` (em-dash). If any surviving disposition is phrased slightly differently (`pending—deferred`, `deferred to Phase 13.2`, hyphen instead of em-dash), the `==0` check passes while a stale "pending" disposition remains in a public doc. The `>=1 blocked-on-host-runtime` check is also game-able (one insertion satisfies it while 4/5 cells still say something else).
- **[LOW] Plan 02 may prematurely edit ROADMAP phase-status for 13.2.** Wave 1's CLOSE-03 consistency pass reads "verify shipped vs deferred… fix drift only." A careless executor could flip 13.2 to complete in ROADMAP before the milestone is actually closed — that's `/gsd-complete-milestone`'s job in Wave 2.
- **[LOW] Hardcoded line numbers** (REQUIREMENTS.md 111/276/144-147/290-293; 13.1-VERIFICATION.md ~182-214) are fragile, though mitigated by the parallel `grep -n` content anchors. Executor should treat content anchors as authoritative.
- **[LOW] Commit-boundary mixing.** Plan 03 Task 1 does an explicit `git add <path> && git commit` for only the verifier report, but authors the SC1 DR + index/log edits without an explicit commit, leaving them to implicit flow. An interruption between Task 1 and Task 2 leaves the DR uncommitted.
- **[LOW] The gate is not re-checked after `/gsd-complete-milestone`.** Archive runs last and may reorganize ROADMAP/STATE; drift reintroduced by archival would go unmonitored. Acceptable since archive is terminal, but worth a post-archive sanity check.
- **[LOW] SC1 reframing-DR is a mild category stretch.** `trigger_type: reframing` per §4.6 is for reframing a *concept/topic*; here it records a *planning success-criterion* renegotiation. It's defensible because the content ("examples/ forms a visually isolable sub-graph") is about wiki graph structure, but it sits at the edge of the decision-record purpose.

## 4. Suggestions

- **Add a hard gate to Plan 01 Task 2:** if any reported count ≠ expected (3/2/2/2/5) or Dataview wasn't enabled / the graph-only Excluded-files pass wasn't reverted, **do NOT flip DEBT-01 to Complete** — record the divergence, leave DEBT-01 Pending, and surface it as a closure blocker (which will correctly make `requirements-sync --strict` exit non-zero and stop Plan 03). The whole point of a human render checkpoint is lost if its result can't block.
- **Rewrite the 13.2-VERIFIER-REPORT.md CLOSE-02 line** to state the honest, weaker claim: "the three CLOSE-02 scenarios are run/audited *now*, after all five phases landed, satisfying the roadmap's temporal 'after' qualifier; `requirements-sync` *separately* confirms documentation consistency for those phases — it is not a functional regression re-run." Drop "the zero-drift gate IS the re-run."
- **Make the Plan 01 Task 3 grep robust to phrasing:** assert `grep -ciE "pending.{0,3}(—|-).{0,3}deferred|deferred to (phase )?13\.2"` returns 0, and assert the count of `blocked-on-host-runtime` equals the expected number of cells (e.g. `>=5`), not `>=1`.
- **Move the host-specific AppArmor detail out of the public doc.** In agent-parity.md, describe the disposition generically ("the reference run was blocked by a host sandbox/user-namespace restriction; cross-agent parity is recorded as accepted-unverified on the maintainer host, with the Claude-vs-golden structural diff carrying the rubric verdict"); keep the literal `apparmor_restrict_unprivileged_userns=1` root-cause in the planning VERIFICATION artifact.
- **Broaden the CLOSE-04 keyword set and unify action/verify scope:** add `event ingest|event stream|webhook|agenda|due date|snooze|recurring|tickler|waiting.?for`, and run the *same* grep scope (`README.md docs/ wiki/ AGENTS.md CLAUDE.md bin/ schema/`) in both the action and the verify line. Require the SUMMARY hit-table to explicitly mark each §14/SQLite hit as "documented future tier (no shipped implementation — confirmed by checking bin/)" vs "shipped."
- **Constrain Plan 02's ROADMAP edits:** explicitly instruct it NOT to change the Phase 13.2 status row or Progress table (those belong to `/gsd-complete-milestone`), only the shipped-vs-deferred narrative.
- **Make Plan 03 Task 1 commit the DR + index/log in the same focused commit** (or immediately after) so an interruption can't strand an uncommitted wiki page.
- **Add a post-archive re-check** in Plan 03 Task 3: after `/gsd-complete-milestone`, re-run `requirements-sync --strict` once and confirm still-green.

## 5. Risk Assessment

**Overall: MEDIUM.**

The mechanical spine is solid and the authors anticipated most of the obvious traps. The risk is concentrated in two places: (1) the human render checkpoint can *observe* a failure but cannot *block* closure as written, which is a direct path to closing on failed verification evidence (HIGH); and (2) the closure record's framing risks asserting more than the tooling proves — both in the "zero-drift = re-run" claim and in the agent-parity disposition. None of these break the verification chain mechanically, and the exit-code gates for CLOSE-01 are genuinely robust and not game-able. With the Task 2 hard-gate added and the two framing corrections, this drops to LOW. Without the Task 2 hard gate, it stays MEDIUM-to-HIGH, because the gate's most human-dependent input is also its least-enforced one.

## Gemini Review

Here is a review of the v1.1 closure verification gate plans.

### 1. Summary

The closure gate is exceptionally well-designed. It correctly translates a meta "verify the verification" milestone requirement into concrete, executable steps without over-engineering new shell scripts. The split across two waves cleanly isolates the human-in-the-loop render checkpoint and the parallelized docs/scope audits (Wave 1) from the final mechanical milestone-wide assertion and archiving (Wave 2). The logic that the `requirements-sync --strict --require-complete` gate mechanically proves the "re-run" assertion for previously landed phases is sharp, accurate, and prevents the LLM from hallucinating fake validation runs.

### 2. Strengths

- **Dependency and Wave Management:** Flawless parallelization in Wave 1. Plan 01 and Plan 02 touch completely disjoint sets of files, allowing the human GUI render and the autonomous scope audit to run concurrently without race conditions.
- **Honesty in Parity Reporting:** Acknowledging the Codex bubblewrap limitation as a `blocked-on-host-runtime` issue rather than faking a "match" or attempting dangerous `sudo` remediations upholds strict engineering integrity.
- **Robust Milestone Assertion:** Reusing the recently delivered `requirements-sync.sh --require-complete` flag guarantees a deterministic, mechanical exit-0 proof that no v1.1 requirement was left behind.
- **Attention to Detail:** Plan 01 correctly updates the frontmatter `score:` in `13.1-VERIFICATION.md` to reflect the newly completed DEBT-01 task.

### 3. Concerns

- **[MEDIUM] Fragile `<automated>` scope-leak verification:** In Plan 02, the automated verification uses a piped `grep -viE` to filter out legitimate boundary/anti-feature mentions. Because `grep` operates line-by-line, if a document states "This is not a \n task engine" across two lines, the negative grep will fail to exclude it, resulting in a false-positive test failure. Additionally, the automated regex drops terms like `sqlite` and `database-backed` that were present in the action's grep.
- **[MEDIUM] Dangerous autonomous deletion instruction:** Plan 02 Task 2 instructs the agent: *"If any hit is a genuine LEAK, fix it inline (remove the leaked capability/doc...)"*. While it is highly unlikely a real task engine leaked into the code, instructing the agent to autonomously delete "leaked capabilities" without human review or running tests could severely break the codebase if a false positive is encountered.
- **[LOW] Staging cross-contamination risk:** In Plan 03 Task 1, the commit is structured as `git add <file> && git commit -m "..."`. If there are any stray staged changes in the index from previous operations, they will be accidentally included in this commit.
- **[LOW] Uncommitted closure artifacts before archive:** Plan 03 Task 2 authors `13.2-VERIFICATION.md`, `13.2-VERIFIER-REPORT.md`, and modifies `REQUIREMENTS.md`. Task 3 immediately runs `/gsd-complete-milestone`. If that script requires a clean working tree or does not automatically commit these artifacts, the milestone could be archived leaving the closure proofs as uncommitted dirty state.

### 4. Suggestions

- **Refine the scope-leak test:** Remove the brittle negative pipe (`| grep -viE ...`) from Plan 02's `<automated>` verification block. Rely on the agent's LLM classification table in the SUMMARY as the primary proof, or use a simpler grep that just checks if the LLM generated the hit-table correctly. Ensure all GTD terms (e.g., `todo`, `to-do`, `sqlite`) are consistent between the action and the test.
- **Halt on genuine leaks:** Change the instruction in Plan 02 Task 2. If a genuine code leak is found, the agent should **halt and request human intervention**, rather than attempting to delete the capability inline.
- **Targeted commits:** In Plan 03 Task 1, use `git commit -m "..." <file_path>` instead of `git add` to guarantee only the specific verifier report is committed, regardless of index state.
- **Commit closure artifacts:** Add a step at the end of Plan 03 Task 2 (or the beginning of Task 3) to explicitly `git add` and `git commit` the `13.2-*` verification reports and `REQUIREMENTS.md` before invoking the milestone archive script, ensuring the milestone closes on a clean tree.

### 5. Risk Assessment

**LOW.** The underlying architecture of the closure gate is rock-solid. It leans heavily on deterministic, pre-existing mechanical gates (`requirements-sync.sh`, `check-neutrality.sh`) and explicitly prevents the agent from making up fake verification data. The concerns identified are isolated to brittle bash tests and edge-case "what if" behaviors that are easily mitigated by tweaking the prompt instructions.
