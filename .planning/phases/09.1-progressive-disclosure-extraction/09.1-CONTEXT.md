<decisions>
## Implementation Decisions

### Extraction scope
- **D-01:** Extract **§4 worked examples + §16 Appendices A & B**. Full first-wave extraction. Expected save: ~500 lines (1,785 → ~1,285).
- **D-02:** No hard line/token ceiling driving the extraction. Trust the research-recommended cuts; re-evaluate only if the spec still feels load-bearing after extraction. Resolves open research Q2 at `.planning/research/questions.md`.
- **D-03:** **§16 Appendix C (Quick Reference Card) stays inline.** It is a short, scannable, load-bearing summary of the most critical rules and cross-references §3. Extracting it would defeat progressive disclosure by forcing pointer-chasing for a summary. Rationale: the core spec must retain a strong always-loaded usable surface.

### Destination directory for §4 worked examples
- **D-04:** New directory **`schema/examples/<type>.md`** for the six filled-in examples (entity, concept, source-summary, comparison, overview, decision). Parallel to existing `schema/templates/` (empty skeletons). Clean separation: `templates/` = empty, `examples/` = filled-in.
- **D-05:** Do NOT reuse `examples/kahneman/` for §4 bodies — content subjects differ (§4 uses Hinton/Vaswani/deep-learning; kahneman cluster uses Kahneman-specific content). `examples/kahneman/` stays as the existing test-fixture cluster for §§11.1/11.2/12 operational illustrations.
- **D-06:** Do NOT co-opt the existing `docs/reference/examples.md` stub. That file is reserved for Phase 12 DEBT scope (documenting how `examples/` works in Obsidian, `.obsidianignore` graph filtering, safe copy-into-wiki). Phase 9.1 does not touch it.

### §4 subject matter
- **D-07:** **Keep current Hinton / deep-learning / Vaswani subjects** in the extracted files — already neutral (no personal data, passes `.neutrality-denylist.txt` and `bin/check-neutrality.sh`), well-crafted, and the prose carries the illustrative point. No rewrite cost. Extraction is a file move with frontmatter, not a content refactor.

### Inline residue pattern in §4
- **D-08:** Per-type §4 residue shape (uniform across all six sub-sections 4.1–4.6):
  1. Section header + "Purpose" one-liner
  2. "When to use"
  3. Section order (TL;DR → Key Facts → Detail → …)
  4. Required / type-specific frontmatter fields (kept inline — this is normative spec, not illustrative)
  5. **2–3 bullet capsule** — "Example subject: X. Demonstrates A, B, C." — micro-summary of what the extracted worked example illustrates
  6. **Bare pointer:** `See: schema/examples/<type>.md for a concrete filled-in instance.`
- **D-09:** **Match existing cross-reference convention exactly.** Use `See: schema/examples/<type>.md` with the same bare `See:` prefix that §§11.1, 11.2, 12 already use for `See: examples/kahneman/...` pointers. One reader-convention across the spec. Do NOT introduce a new prefix (e.g., "See worked example:") or switch to Markdown-link style — uniform pointer convention pays off.
- **D-09 resolution note (2026-04-16, cross-AI review R1):** The pointer-trailer phrasing is **`for a concrete filled-in instance.`** (singular), matching the exact in-tree precedent at AGENTS.md §§11.1 (line 880) and 11.2 (line 1323); §12 (line 1553) uses the plural `for concrete filled-in instances of these operation patterns.` because it points to a file with multiple worked operation patterns. Earlier drafts of CONTEXT.md / RESEARCH.md / PATTERNS.md briefly drifted to `for a fully worked instance.`; Gemini + Codex cross-review flagged the drift and both the plans/tests and these supporting docs are now aligned on the singular `for a concrete filled-in instance.` phrasing used by §§11.1/11.2. Plan 09.1-02 DR prose records this alignment choice under the "Consequences" section so future-reader cannot relitigate.

### §16 Appendix extraction
- **D-10:** Extract **Appendix A (Dataview Queries)** → **`docs/reference/dataview-queries.md`**. Pure reference; 5 query examples; no agent executes these inline; real standalone value as a queryable cookbook.
- **D-11:** Extract **Appendix B (Commit Message Examples)** → **`docs/reference/commit-examples.md`**. Small (~10 lines) but clearer as its own topical file than bundled with A. Matches the existing `docs/reference/` topic-per-file convention (brownfield.md, privacy-model.md, ci.md, release.md, schema-tour.md, setup-prerequisites.md).
- **D-12:** Do NOT combine A+B into a single `docs/reference/appendices.md` grab-bag. Topic-per-file is the established pattern.
- **D-13:** §16 residue in `AGENTS.md`: brief one-line pointer per appendix ("See `docs/reference/dataview-queries.md`" / "See `docs/reference/commit-examples.md`"), then Appendix C retained verbatim inline.

### Mechanical / required (not gray areas — captured for planner)
- **D-14:** **Decision record required** per §11.4 Tier 1: create `wiki/decisions/dr-2026-04-16-progressive-disclosure-extraction.md` with `trigger_type: schema-update`, `affected_pages: []` (inaugural/infrastructure record — same pattern as the Phase 6 decision-type DR), populating all 7 required sections. This is a significant structural choice that reframes "sole authoritative specification" as "spec + linked deep references" and must be recorded inline as part of the extraction commit.
- **D-15:** **Canonical fixture regeneration.** After `schema/AGENTS.template.md` is edited in parallel with `AGENTS.md`, `schema/fixtures/canonical-AGENTS.md` must be regenerated (python3 str.replace per Plan 08-01) so Phase-08 CI `setup-parity` byte-equality test stays green. This is the Plan 08-01 reference render routine — reuse it verbatim.
- **D-16:** **Byte-equality auto-preserved.** `.githooks/pre-commit` runs `bin/sync-claude.sh --check`; if drift is detected, `cp AGENTS.md CLAUDE.md` re-syncs and re-stages. No manual CLAUDE.md edits needed. Confirmed by inspecting `.githooks/pre-commit` and `bin/sync-claude.sh`.
- **D-17:** **Release allowlist already covers destinations.** `bin/release.sh` ALLOWLIST (lines 18–38) includes `schema` and `docs`, so `schema/examples/*.md`, `docs/reference/dataview-queries.md`, and `docs/reference/commit-examples.md` ship cleanly through the Phase-07 orphan-branch release without allowlist edits.
- **D-18:** **Phase-07 `test_reference_stubs.sh` untouched.** That test asserts `docs/reference/examples.md` is a stub; we chose `schema/examples/` (not `docs/reference/examples/`), so the assertion is preserved. Verified by reading `tests/phase-07/test_reference_stubs.sh` line 13 (expects `docs/reference/examples.md`) and line 20 (STUB_FILES includes it).

<specifics>
## Specific Ideas

- **User rationale for D-08 (capsule + pointer, not bare pointer):** "You already decided to do the deeper extraction with no hard ceiling, that means you can afford a small amount of inline context. A micro-summary preserves readability and reduces the risk that the core spec becomes too skeletal. It still gives you almost all the savings, without keeping a full example inline. A good residue shape per type is: purpose / when to use, section order, required frontmatter, 2–3 bullets saying what the worked example demonstrates, See: schema/examples/<type>.md."
- **User rationale for D-09 (match existing `See:` convention):** "Keep the reader convention uniform. The spec already uses See: ... Changing §4 to a new prefix or Markdown-link style would introduce an unnecessary second pattern."
- **User rationale for D-03 (keep Appendix C inline):** "The quick reference card is exactly the kind of thing that belongs in the core spec — short, scannable, load-bearing. Extracting it would make the core less usable, not more progressively disclosed."
- **User rationale for D-12 (topic-per-file, not combined appendices.md):** "dataview-queries.md has real standalone value; commit-examples.md is small but still clearer as its own topical file. This matches the existing docs/reference/ pattern better than a grab-bag appendix file."
- **Phase framing:** This is an INSERTED urgent phase between Phase 9 (complete) and Phase 10 (brownfield scan+bootstrap). v1.1 Shareability milestone is otherwise 3/5 complete; Phase 9.1 must not widen scope into workflow/operation extraction or re-architecture.
