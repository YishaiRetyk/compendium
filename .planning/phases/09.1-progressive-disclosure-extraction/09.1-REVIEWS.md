# Cross-AI Plan Review — Phase 09.1 Progressive Disclosure Extraction

## Gemini Review

The implementation plans for **Phase 09.1: Progressive Disclosure Extraction** are of exceptional quality and are fully ready for execution. They demonstrate a sophisticated understanding of the project's structural invariants, specifically the byte-equality requirements and the dual-track (wizard vs. manual) parity. The strategy for atomic extraction, supported by a comprehensive test scaffolding wave, effectively mitigates the risk of drift between the specification and its user-facing templates.

### Strengths

*   **Robust R-1 Mitigation (Template Parity):** The plan strictly enforces parallel edits to `AGENTS.md` and `schema/AGENTS.template.md` within the same commit. This is critical for ensuring that users on both the manual and guided setup tracks receive the same updated specification.
*   **Uniform Pointer Convention:** By matching the existing `See: examples/kahneman/...` pattern at §§11.1, 11.2, and 12, the plan preserves a consistent reader experience for both human maintainers and LLM agents doing progressive disclosure.
*   **High-Fidelity Content Preservation:** The use of verbatim extraction for the worked examples and appendices ensures that the "sole authoritative specification" remains functionally complete despite being physically distributed.
*   **Comprehensive Validation:** The 10-test aggregator in `tests/phase-09.1/` covers 15 distinct structural invariants (I-1 through I-15), including byte-equality, YAML validity, and residue shape. The inclusion of current-state canaries (e.g., `test_template_parity.sh`) prevents regressions during the move.
*   **Infrastructure Alignment:** The plan correctly identifies the need to regenerate the canonical fixture and update the `wiki/index.md` with a new `## Decisions` section, fulfilling Tier-1 inline decision record obligations (§11.4).

### Concerns

*   **[MEDIUM] Reduction Shortfall vs. Target:** The actual reduction (~350 lines) is lower than the initial headline estimate (~500 lines). The plan acknowledges this in the Decision Record "Consequences" section, noting it is the cost of retaining 2-3 bullet capsule summaries for readability. This is a sound engineering tradeoff, but it should be called out during verification to ensure stakeholder alignment.
*   **[LOW] Pointer Phrasing Discrepancy:** `CONTEXT.md` (D-08) suggests "fully worked instance" while Plan 01/02 uses "concrete filled-in instance." The latter actually matches the existing repo precedent in §11.1 exactly. I recommend sticking with the plan's internally consistent choice of **"concrete filled-in instance"** to maximize consistency.
*   **[LOW] Pre-commit Hook Interaction:** The `.githooks/pre-commit` behavior (exiting 1 on sync) is correctly identified as a feature, but it may require the executor to attempt the commit twice. This is well-documented in the task instructions.

### Suggestions

*   **Log Activity in `wiki/log.md`:** Although Plan 02 updates `wiki/index.md`, it does not explicitly mandate a log entry for the extraction. To comply with §9's "all wiki mutations use a formal operations vocabulary" rule, consider adding a `reflect` entry to `wiki/log.md`:
    ```markdown
    ## [2026-04-16] reflect | progressive disclosure extraction

    result: extracted §4 worked examples and §16 appendices to deep-reference files
    reason: reduce spec context size while preserving authoritative framing (DR-2026-04-16-progressive-disclosure-extraction)
    ```
*   **Ratchet the preamble check:** In `tests/phase-09.1/test_agents_section_4_residue.sh`, consider adding a check for the "Six page types" polish:
    ```bash
    grep -q 'Six page types exist\.' "$A" || { echo "FAIL: §4 preamble not updated to 'Six'" >&2; exit 1; }
    ```
*   **Verify `dataview-queries.md` Nested Fences:** When extracting Appendix A, ensure the 6-backtick markdown fences wrapping the 3-backtick dataview fences are preserved verbatim as planned. This prevents the reference doc from trying to execute the dataview queries itself rather than displaying them as code samples.

### Risk Assessment

**Overall Risk: LOW**

The mechanics of the extraction are well-understood, the line ranges have been verified by direct inspection, and the validation suite is robust enough to catch the primary failure modes (drift, malformed YAML, or missing pointers). The dependency on the Plan 08-01 render routine for fixture regeneration is the most sensitive moving part, but it is handled as a verbatim script reuse, which is low-risk.

**Approval:** READY FOR EXECUTION.

## Codex Review

### Summary

The plans are strong overall: they are detailed, test-driven, and correctly treat Phase 09.1 as an atomic Wave-0 scaffolding plus Wave-1 extraction. The key execution premise is valid in the current repo: `AGENTS.md` and `schema/AGENTS.template.md` have identical §4 and §16 bodies today, both prior decision records exist, and `bin/check-privacy.sh` really does only scan frontmatter in public paths. The main issues are not structural feasibility but plan drift and over-specification: there are a few wording mismatches between locked decisions and the test suite, one standalone-doc formatting mistake around nested fences, and a couple of tests that are slightly more permissive or brittle than the stated requirements.

### Strengths

- The plan is grounded in real repository state, not assumptions. The parity premise for §4 and §16 is currently true, and the cited decision records exist.
- The Wave-0/Wave-1 sequencing is mostly sound. Canary tests first, then RED extraction tests, then a single Green commit is the right shape for this kind of prose refactor.
- The most important regression risks are explicitly modeled:
  - `AGENTS.md` vs `CLAUDE.md` byte equality
  - `AGENTS.md` vs `schema/AGENTS.template.md` parity
  - canonical fixture regeneration via the Phase-08 routine
  - preservation of the Phase-07 `docs/reference/examples.md` stub
- `test_template_parity.sh` is a good idea. Its `awk` extraction avoids hard line-number coupling, which is exactly what this phase needs.
- The inline decision record requirement is correctly included in the same change, not deferred.
- The `wiki/index.md` update is well chosen. The file currently has no `## Decisions` section, so creating one is a real completeness improvement.
- The privacy reasoning for `docs/reference/*.md` is correct with respect to the current implementation of `bin/check-privacy.sh`: no frontmatter means that specific guard has nothing to flag.
- The expected pre-commit double-run behavior for `CLAUDE.md` is documented, which reduces operator confusion during execution.

### Concerns

- **[HIGH]** There is a direct wording inconsistency between the locked phase context and the executable plans for the §4 pointer text. The context/research/patterns repeatedly specify `See: schema/examples/<type>.md for a fully worked instance.`, while Plan 09.1-01 and 09.1-02 hard-code `for a concrete filled-in instance.` The tests enforce the latter. This is exactly the kind of tiny spec drift that creates churn later.
- **[HIGH]** The extraction plan for `docs/reference/dataview-queries.md` says to preserve the outer ` ```markdown ` fence around each inner ` ```dataview ``` block. That makes sense inline inside `AGENTS.md`, but it is wrong for a standalone reference doc. In the extracted file, those outer fences will render the Dataview snippets as literal Markdown examples rather than direct query snippets.
- **[MEDIUM]** `test_decision_record.sh` is looser than the requirement. The plan says `affected_pages: []`, but the test accepts either `[]` or `None`. That weakens a locked requirement and could let an incomplete DR pass.
- **[MEDIUM]** `test_byte_equality.sh` does not fully match its own narrative. The plan text says it re-invokes the Phase-08 canonical byte-equality test and the pre-commit sync check, but the actual script only does `cmp -s AGENTS.md CLAUDE.md` plus the Phase-08 test. That is probably fine, but the spec and the test are out of sync.
- **[MEDIUM]** The privacy claim is only half the story. `bin/check-privacy.sh` will indeed ignore frontmatter-free docs, but `bin/check-neutrality.sh` scans public docs body text, not frontmatter only. So "no frontmatter means safe" is true for privacy, not for neutrality. The plan sometimes blends those two arguments too casually.
- **[MEDIUM]** The canary/RED transition depends on the exact current text of Appendix C and the exact former §4 strings. Some of the proposed greps in acceptance criteria are brittle or malformed, especially the regex shown as `Read .wiki/index\.md. first, always`, which is not the actual literal text.
- **[MEDIUM]** The plan is slightly over-engineered in prose. The per-type 2–3-bullet capsule is defensible, but the plans then spend a lot of effort freezing exact capsule wording, exact commit body, exact DR prose, exact wiki/index additions, and optional index updates. That increases execution surface without adding much safety.
- **[LOW]** The "Five→Six page types exist" polish is reasonable, but it is still scope expansion beyond the explicitly stated extraction. It is harmless, but it should be framed as opportunistic cleanup, not mandatory success criteria.
- **[LOW]** The verification count in Plan 09.1-01 appears inconsistent. It describes 12 files total under `tests/phase-09.1/`, but one check says `ls tests/phase-09.1/*.sh | wc -l` returns 11. With `run.sh`, `lib.sh`, and 10 test files, the count should be 12.
- **[LOW]** The commit subject `schema(09.1): ...` is probably acceptable, but AGENTS only documents `schema:` examples, not scoped `schema(...)`. If there is any strict validation around commit examples later, this could become avoidable noise.

### Suggestions

- Align the pointer text everywhere before execution. Pick one phrase and use it consistently in:
  - `09.1-CONTEXT.md`
  - `09.1-RESEARCH.md`
  - `09.1-PATTERNS.md`
  - both plan files
  - all tests
  Given the locked decision text, I would use `for a fully worked instance.` and update the plans/tests to match.
- Change the extracted `docs/reference/dataview-queries.md` format so it contains direct ` ```dataview ` blocks, not nested outer ` ```markdown ` wrappers. The outer wrappers are correct in `AGENTS.md` as illustrative inline Markdown; they are not correct in a standalone cookbook file.
- Tighten `test_decision_record.sh` to require exactly `affected_pages: []`. The current allowance for missing/`None` undercuts D-14.
- Make `test_byte_equality.sh` either:
  - actually run `bash bin/sync-claude.sh --check`, or
  - stop claiming that it does.
  Right now the prose and implementation diverge.
- Simplify the capsule requirements. Keep D-08's residue shape, but do not freeze exact capsule wording so aggressively in the Wave-1 execution plan. The test should verify presence of the pointer and absence of the old worked example body, not police prose that has no behavioral effect.
- Soften the "Five→Six" change from mandatory to optional cleanup. It is a good fix, but it is not necessary to achieve the phase goal and shouldn't block the extraction if something else gets noisy.
- Fix the Appendix C verification strings to match the literal current text exactly. The acceptance criteria version with `Read .wiki/index\.md. first, always` is too error-prone.
- Add one explicit preflight in Wave-1 before editing:
  - run `bash tests/phase-09.1/test_template_parity.sh`
  - if it fails, abort the phase rather than proceeding with offset-based dual-file edits
  That makes the "current parity premise" an enforced precondition, not just a documented assumption.
- Consider dropping Step 8's optional `docs/reference/index.md` update from the execution plan. It is harmless, but it weakens the "atomic extraction only" boundary and adds one more file that future reviewers have to reason about.

### Risk Assessment

**Overall risk: MEDIUM**

The plans will probably deliver the intended outcome: the extraction is mechanically feasible, the byte-equality and canonical-fixture safeguards are real, and the current repo state supports the dual-file edit strategy. The main risk is not failure to implement the move, but failure through plan inconsistency: pointer wording drift, a slightly wrong extracted Dataview format, and a few tests that are either too loose or too brittle. Fix those before execution and the risk drops to low.

### Agreed Concerns (highest priority — both reviewers flagged these)

- **`docs/reference/dataview-queries.md` nested-fence handling** — Codex flagged this as **[HIGH]** (the outer ` ```markdown ` fence renders queries as literal markdown examples, not snippets).
