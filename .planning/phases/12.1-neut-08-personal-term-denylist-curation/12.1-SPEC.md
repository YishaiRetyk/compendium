## Constraints

- **No engineering changes to the neutrality gate.** All denylist additions must work under the existing `bin/check-neutrality.sh` matching semantics (case-insensitive substring match per the existing `term in scrubbed` loop). If a candidate term cannot be added without false positives across legitimately neutral text, it is rejected — not "fixed" by gate changes.
- **Curation rubric is binding.** Promote terms only if (a) proper noun / personal name / project codename, OR (b) multi-word phrase or hyphenated identifier unique to the personal vault. Reject all generic single-word English vocabulary regardless of source. The 19-token `agents-md-size-risk.md` cluster is expected to yield approximately zero promotions.
- **Categorization is mandatory.** Every promoted term lives under an explicit `# Category:` header (with optional `#`-comment rationale lines). Bare lines outside a category fail acceptance.
- **Frontmatter precedent is binding.** The `wiki/maintenance/lint-report.md` fix uses `neutrality_exempt: true` exactly — same key, same value, same placement in the existing frontmatter block — to mirror the three established precedents. No new frontmatter fields, no rewording of the existing key.
- **Test fixture must seed a freshly promoted term.** A pre-existing Kahneman or personal-decision term does not satisfy requirement #3 — the fixture's job is to prove the new entries wire correctly.
- **CI workflow must remain unchanged.** `.github/workflows/neutrality.yml` invokes `bin/check-neutrality.sh` as-is; the curated denylist must satisfy that invocation without workflow edits.
